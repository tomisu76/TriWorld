# TriWorld persistent project instructions

These rules apply to every AI session and every development phase until the
project is released. This file contains durable policy, not the current task.
Never copy a temporary experiment, model choice, artifact hash, or phase-specific
prompt into this file.

## Mandatory session bootstrap

Do not begin with a plan or a summary. First prove that this session can read the
real workspace and execute tools.

1. Run `git -C C:\TriWorld rev-parse HEAD` and
   `git -C C:\TriWorld status --short --branch`.
2. Return the literal output internally; do not replace it with a snapshot,
   remembered value, expected value, or prose.
3. If either command cannot actually run, stop. State `TOOL ACCESS NOT PROVEN`
   and do not audit, edit, build, install, launch, commit, or push.
4. Read `docs/CURRENT_HANDOFF.md`.
5. Read `docs/hints/HERMES_VERIFICATION_RULES.md`.
6. Read `HERMES_START_HERE.md`.
7. Inspect the relevant source, artifact, log, and diff for the current task.

Continue from the checkpoint. Do not restart Phase 0, repeat completed research,
or re-open a closed experiment unless the user asks for it or stronger evidence
proves the checkpoint wrong.

When the user has already authorized read-only inspection, execute it without
asking “may I continue?” or repeating the proposed commands. A response that only
says “I will run” is not progress. Ask for approval only before an action that
actually requires new authority.

`HERMES_TRIWORLD_MASTER_PROMPT_2026.md` is the long-term product and architecture
specification. It is not the current task queue and is not mandatory reading in
full on every session.

If prose, Git, generated artifacts, installed artifacts, tests, screenshots, or
runtime logs disagree, pause mutation and reconcile the conflict. Prefer direct,
reproducible evidence over summaries.

## No simulated evidence

Never present a planned command, pseudocode, inferred value, placeholder, or
abbreviated example as an executed result.

- An executed-command report includes the exact command, exit status, and
  literal relevant output.
- `<hash>`, `<hash1>`, `...`, “etc.”, invented paths, and shortened arrays are
  forbidden in evidence.
- “Machine-derived” means a command actually ran against the named file. Quote
  raw output or preserve the complete output at an identified path with SHA-256.
- Never invent function names, schemas, ZIP entries, source lines, commands, or
  expected test counts. Read them from the current tree.
- Label every unexecuted command and expected result as `PROPOSED`.
- Report command failures; never replace them with the expected result.
- Never claim a command ran merely because it is syntactically plausible.
- A fake or patterned hash, placeholder, impossible file size, nonexistent path,
  or mismatch with a trivial independent command invalidates the entire report.
- After one invalid evidence report, stop mutation and repeat only the smallest
  capability probe. After a second invalid report, state that the session is not
  reliable for repository work and hand off.

## Permanent product goal

TriWorld must turn a user-selected real-world area into a deterministic,
portable BeamNG.drive level ZIP that:

- is discoverable and loadable in the pinned BeamNG target;
- has plausible terrain and correctly aligned physical roads;
- has continuous vehicle collision and useful road materials;
- has AI navigation where declared;
- has safe spawns, environment, lighting, and required gameplay metadata;
- records provenance, licenses, versions, validation, and build evidence;
- can be reproduced from the same locked inputs;
- does not redistribute protected stock game content.

A ZIP, a preview, or a static validator PASS alone is not completion.

## Permanent engineering boundaries

- Keep source acquisition, geospatial normalization, terrain, road topology,
  physical mesh, visual layers, collision, AI graph, gameplay, validation, and
  packaging as explicit stages with versioned contracts.
- `DecalRoad` is not physical collision. SUMO is not a 3D road mesh. A rendered
  road does not prove drivability or AI routing.
- Never guess BeamNG serialization, Lua, editor, terrain, material, or scene
  formats. Verify against the exact pinned runtime, engine-saved golden data,
  stock examples where legally available, and a minimal runtime canary.
- Treat Italy as a quality benchmark and optional local dependency, never as a
  redistributable asset pack. Generated packages may reference stock assets only
  when the dependency is declared and verified for the pinned version.
- Preserve unrelated user changes. Never reset or clean a dirty worktree.
- Do not expose secrets or personal paths in committed evidence.
- Do not edit agent skills, global model routing, installed mods, game caches, or
  external systems unless the current request places them in scope.
- Commit and push only when authorized. A commit must not mix unrelated work.

## Development loop for every phase

1. Establish the exact baseline, target version, scope, and evidence.
2. State the smallest falsifiable hypothesis or acceptance criterion.
3. Preserve the failing input, artifact, hash, and relevant log.
4. Make the smallest source-level change; do not patch generated ZIPs manually.
5. Add a positive test and an adversarial regression test where applicable.
6. Run the narrow tests, then the proportionate wider suite.
7. Generate a new immutable artifact through the normal pipeline.
8. Record its SHA-256 and compare its contents with the previous artifact.
9. Run static and integration gates.
10. Run the pinned BeamNG/SUMO/Blender runtime gate when the claim requires it.
11. Classify every result using the evidence states in the verification rules.
12. Update the current handoff and implementation inventory before transfer.

One experiment uses one immutable artifact. A content change requires a new
identity and hash. Names such as `fixed2` or `final-final` are not evidence.

Before an isolation experiment, prove that its variable is not already present
in current source. Compare the exact baseline artifact, a fresh current-generator
artifact, and the installed artifact. Source containing multiple later changes
is not a single-variable baseline until byte equivalence is restored and proven.

Do not execute untracked helper scripts merely because they exist. Treat
`build_canary.py`, `build_e2b.py`, `patch_*.py`, `read_*.py`, and `scratch/` as
untrusted workspace residue unless the current handoff explicitly validates and
authorizes a specific file.

## Phase and release discipline

- A phase may close only when its documented acceptance gates pass.
- Do not silently weaken a gate to match the current implementation.
- `not_applicable` requires a written reason; `not_run` is not a pass.
- Runtime verification applies only to the exact artifact and environment tested.
- Re-test downstream gates when an upstream contract or serialized output changes.
- Before release, require a clean reproducible build, complete evidence report,
  license/provenance review, clean target-runtime logs, drive/AI checks appropriate
  to the generated map, and installation from the distributed ZIP.

## Required handoff

At the end of meaningful work, replace stale facts in:

- `docs/CURRENT_HANDOFF.md` — concise current execution state and one next action;
- `docs/implementation-status.md` — durable capability and gate inventory.

Never append chat transcripts or repeated reports. Record exact commands, counts,
hashes, environment, remaining uncertainty, dirty files, and whether changes are
committed or pushed. A future session must be able to continue without replaying
the project history.
